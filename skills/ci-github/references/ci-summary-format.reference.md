# CI 結果サマリ形式

## 理解できること

provider の step/job summary と、CI 外で確認する標準出力を、人が短時間で読める同じ形式に揃えるための列構成、表示順、欠測時の表記。

## 適用範囲

- provider の summary sink へ出力する CI スクリプト
- CI 外で結果を確認する補助スクリプトの標準出力

実行結果の意味と `status`、`evidence` の契約は `references/ci-preset-contracts.reference.yml` および `references/ci-script-contracts.reference.yml` を正本とする。`collection` と欠測時の表示規則はこの参照が定義し、ジョブやパイプラインの確定結果を再定義しない。

## 基本形式

ジョブサマリとテストサマリは、同じ3列の表で出力する。

```markdown
## ジョブサマリ

| ジョブ | 実施 | 結果 |
|:--|:--|:--:|
| `{job id}` | {短い実施内容} | {結果} |

## テストサマリ

| テスト | 実施 | 結果 |
|:--|:--|:--:|
| `{test unit}` | {短い実施内容} | {結果} |
```

## 監査報告の形式

監査では、事前検証、機械監査、意味監査、監査全体の結果を同じ `success` として表示しない。次の区分を分け、記載順も維持する。

| 区分 | 判定 |
|:--|:--:|
| 事前検証 (`preflight`) | {成功 / 失敗 / blocked / 未実施} |
| 機械監査 (`machine-audit`) | {成功 / 失敗 / blocked / 判定不能 / 未実施} |
| 意味監査 (`semantic-audit`) | {成功 / 失敗 / blocked / 判定不能 / 未実施} |
| 監査全体 (`overall-audit`) | {成功 / 失敗 / blocked / 判定不能 / 未実施} |
| 適合 (`conformance`) | {適合 / 不適合 / 判定不能 / 未実施} |

`provider-preflight` しか完了していない場合、機械監査、意味監査、監査全体、適合を `成功` や `適合` として表示しない。各区分のstatusは `ci-audit-contract.reference.yml` の `statusClassification`、`statusAggregation`、`reporting` から導出する。

各区分の入力、owner、status導出、集約順序、適合条件は `ci-audit-contract.reference.yml` を正本とし、本書では再定義しない。意味監査subjectの報告項目は `ci-audit-subjects.reference.yml` を正本とする。問題点、未確認範囲、推奨修正案、理想案、具体的な修正計画の必須項目は、review スキルのレポート要件を正本とする。CI監査では上表と、各statusに対応するフェーズ、証拠provenance、意味監査subjectの結果、意味候補の判断結果をreview報告へ追加する。repository 内の CI 関連文書は、subject catalog の `repository-ci-documentation.reportingFields` に従って適用対象ごとに報告し、対象がない場合は同 subject の `inapplicable` に従う。事前検証の `success` や文書の存在確認だけを監査報告の結論にしない。

各フェーズと意味監査subjectの詳細には、証拠取得の実施区分を `executed` または `reused` で表示する。`reused` は今回の対象、契約、実行条件へ適用できることを確認した証拠を示し、監査statusを変更しない。cache miss は証拠を取得し直した後のstatusと分離し、キャッシュ保存失敗は監査結果を変更しない警告として詳細へ記録する。

### 表示規則

1. ジョブサマリとテストサマリは、それぞれ1つの表にまとめる。
2. 列は `単位`、`実施`、`結果` の3列とし、列名はジョブでは `ジョブ`、テストでは `テスト` とする。
3. `実施` は、その単位で何を行ったかを短い動詞句で記載する。コマンド全文やログ全文は出力しない。
4. `結果` は `✅ 成功`、`❌ 失敗`、`⚠️ 判定不能`、`⏭ 未実施`、`⏭ 対象外` のいずれかを基本値とし、件数を付加してよい。`対象外` は設計または owner 契約により実行しない単位を表し、実行状態ではないため集約と required check の判定から除外する。実行すべき単位が実行されなかった場合は `未実施` を使う。
5. `結果` は job status だけでなく、実行した処理の outcome と evidence から導出する。
6. 失敗、判定不能、未実施、対象外の理由と機械値は表の下の詳細へ分離し、必要な場合だけ表示する。
7. 詳細では、`判定`、`収集`、`対象`、件数、失敗、理由を別項目として保持する。入力に存在しない値を `0` や成功値で補完しない。
8. 必須件数が不足する、または件数の合計が矛盾する場合は `収集: 一部取得` と `判定: 判定不能` を表示する。明示的な失敗結果は `判定: 失敗` を優先する。
9. 結果または証拠を取得できない場合は、表の `結果` を `⚠️ 判定不能` または `⏭ 未実施` とし、詳細に理由を残す。
10. job ID、result ID、パス、version などの機械値は inline code として表示し、ログ由来の改行は1行へ正規化する。
11. サマリの表示状態は job または pipeline の確定結果を上書きしない。

### 詳細形式

テスト単位の詳細は、表の下に `<details>` で折りたたんで表示してよい。詳細内では次の順序を維持する。

```markdown
### {summary title} テスト結果
- 判定: {成功|失敗|判定不能}
- 収集: {完了|一部取得|取得不可}
- 対象: `{対象}`
- スイート: {n}件（成功 {n}件 / 失敗 {n}件）
- テスト: {n}件（成功 {n}件 / 失敗 {n}件 / スキップ {n}件 / TODO {n}件）
- 失敗:
  - {失敗名}
- 理由: {短い補足}
```

失敗詳細は最大10件を表示し、残りがあれば `ほか {n}件` として件数だけ示す。

## 例

### 成功

```markdown
## テストサマリ

| テスト | 実施 | 結果 |
|:--|:--|:--:|
| `unit` | unitテストを実行 | ✅ 成功（42件） |
```

### 失敗

```markdown
## テストサマリ

| テスト | 実施 | 結果 |
|:--|:--|:--:|
| `integration` | integrationテストを実行 | ❌ 失敗（2件） |

<details>
<summary>失敗の詳細</summary>

### integration テスト結果
- 判定: 失敗
- 収集: 完了
- テスト: 12件（成功 10件 / 失敗 2件 / スキップ 0件）
- 失敗:
  - API returns 401
  - API returns 403

</details>
```

### 入力不備

```markdown
## テストサマリ

| テスト | 実施 | 結果 |
|:--|:--|:--:|
| `unit` | unitテストを実行 | ⚠️ 判定不能 |

<details>
<summary>判定不能の理由</summary>

- 判定: 判定不能
- 収集: 取得不可
- 理由: テストレポートが見つからないか、形式が不正です

</details>
```
